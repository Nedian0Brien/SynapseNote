SynapseNote keeps v2 scalar values in a marker-delimited owner Markdown table,
links each document entity with `[[wikilink]]`, and stores schema/views in a
versioned manifest. v1 record-per-file databases remain readable and are
converted only through an explicit preview/approval task. Imports therefore
distinguish lossless content conversion from features that require a new schema
or manual review.

## v1 → v2 database migration

Migration is a durable, write-frozen task rather than background synchronization.
The preview inventories every source record, exact before hash, typed cell
conversion, document identity, relation target, title conflict, owner path, and
bounded lifecycle/audit/layout alias. Apply is refused for unresolved index
issues, unsafe paths, duplicate identities, unsupported cells, relation/derived
blockers, or size-limit overflow.

The task records a plan hash, approval binding, before/after bytes, and
checkpoint journal under the project-local operational state. A restart restores
the migration gate; clean rollback is retryable, while unknown external bytes
become `recovery_required` instead of being overwritten. After cutover, a cold
rebuild verifies the owner table and linked documents before the task reports
success. Existing v1 files are not auto-migrated and are not dual-written.

For the exact state machine, file limits, rollback boundaries, and fixture
matrix, see [RFC 0008](https://github.com/Nedian0Brien/SynapseNote/blob/main/docs/rfcs/0008-markdown-table-canonical-database-storage.md)
and its [implementation checklist](https://github.com/Nedian0Brien/SynapseNote/blob/main/docs/rfcs/0008-markdown-table-database-storage-implementation-checklist.md).
The v1 reader/export/import compatibility window and product-edit guard are recorded in
[RFC 0009](https://github.com/Nedian0Brien/SynapseNote/blob/main/docs/rfcs/0009-database-v1-compatibility-retirement.md).

## Source matrix

| Source                       | Entry point                                               | Carries over                                                                                 | Requires review or has loss                                                                                                                                                |
| ---------------------------- | --------------------------------------------------------- | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Notion Markdown & CSV export | `ok migrate notion <folder>` or the Database CSV/TSV flow | Pages, headings, basic tables, row Markdown, simple property values, attachments, title/body | Relations, rollups, formulas, comments, history, backlinks, synced blocks, icons/covers, and database automations are not represented by the export and must be recreated. |
| CSV/TSV                      | Database creation/import preview                          | Title, strict numbers, booleans, ISO dates, select/status labels, stable `record_id` updates | Derived Formula/Rollup columns are read-only; malformed or ambiguous values block planning; files and relations need explicit typed mapping.                               |
| Plain Markdown               | Existing-folder onboarding                                | Existing paths, body, frontmatter, titles, and external links                                | Stable record IDs are assigned only after a blocker-free onboarding preview; unsupported frontmatter stays preserved and diagnosable.                                      |
| Obsidian vault               | Open the vault directly                                   | Markdown, wiki links, tags, frontmatter, callouts, math, Mermaid, footnotes, and assets      | `.obsidian` settings/plugins, Dataview, Canvas/Bases interactivity, transclusion, and block references are not database semantics.                                         |

## Notion export workflow

1. Export the workspace as **Markdown & CSV**.
2. Run `ok migrate notion <export-folder>` to preview deterministic transforms.
3. Review the JSON report and known-loss table before `--apply`.
4. Open the cleaned folder in SynapseNote.
5. Use Database creation from CSV/TSV for a typed source, then use the existing
   folder onboarding flow for row pages when preserving their original paths is
   important.

The migration command is idempotent and dry-run by default. It does not delete
CSV files unless `--remove-csv` is explicitly supplied.

## Loss and recovery rules

- A lossy or unsupported object is reported by name and category; it is never
  silently presented as a complete database.
- Existing Markdown and imported source files remain recoverable through Git and
  the transaction receipts.
- Schema conversion previews list invalid, lossy, dependent, and blocked rows
  before any canonical write.
- Relations and formulas should be recreated with stable property IDs after the
  source schema is accepted; do not infer them from display labels alone.
