# RFC 0010 database row-write optimization report

- 기준일: 2026-07-31
- 범위: v2 markdown owner-table 행 쓰기 경로 — 인덱스, writer, shadow repo, 클라이언트 갱신
- 브랜치: `codex/fix-row-latency-cv-fidelity` (`85a16cbf` → `d12d90ed`)
- 측정기: `packages/app/tests/perf/profile.ts --scenario=database-row-insert`
- 판정: **워크스트림 종료.** 쓰기 비용은 테이블 크기와 무관함이 300행에서 확인됨

## 결론부터

행 삽입은 300행 테이블에서 p50 **146ms**이고, **쓰기 자체는 테이블 크기에 비례하지 않습니다**. `mutate`의 마지막 1/4은 40행 런에서 67ms, 300행 런에서 72ms입니다.

더 최적화할 근거가 없어 종료합니다. 남은 유일한 실제 기울기는 읽기(`query`)의 9ms → 43ms이고, 300행에서 43ms는 쫓을 가치가 없습니다.

## 성과

측정은 커밋별로 다른 환경에서 이루어졌습니다. **단계 안에서만 비교 가능하며, 전 구간을 하나로 이어 붙일 수 없습니다** — 측정 방법 자체가 작업 도중에 교체되었기 때문입니다(아래 "측정 신뢰성" 참조).

## 성능 작업이 찾아낸 정합성 버그

전부 크래시 없는 **조용한 오염**입니다.

| 커밋 | 버그 |
| --- | --- |
| `d44ccb3d` | 의존성 문서가 위키링크 해석 후보 |
| `a74e57ed` | 모든 v2 행 생성이 가짜 `invalid_record` 이슈를 남김 — 전체 리빌드만 청소 |
| `a51f31b2` | **유니크 제약이 증분 쓰기 후 한 번도 재계산되지 않음** — 외부 편집이 만든 중복을 전체 리빌드만 발견 |
| `a51f31b2` | clear가 relation/person 셀에서 링크된 문서를 삭제 — 그 문서가 다른 소스의 행이면 파괴 |

뒤의 셋은 `database-record-index-incremental-equivalence.test.ts`가 잡았습니다. "증분 적용 결과 == 전체 재빌드 결과"를 `snapshot().revision`으로 비교하는 테스트이며, **델타 구현 전에** 만들었기 때문에 기존 버그와 신규 버그를 구분할 수 있었습니다.

## 측정 신뢰성

이 워크스트림에서 가장 값비싼 교훈은 최적화가 아니라 측정에 있었습니다. **결론 네 개를 철회했습니다.**

| 증상 | 실제 원인 |
| --- | --- |
| "클라이언트가 875ms 논다" | in-app 브라우저가 `visibilityState: hidden` → Chromium이 타이머를 ~1Hz로 클램프. `setTimeout(75)`가 236/1000/1000ms |
| "`open` 깜빡임" | 별개의 두 컴포넌트 로그가 시간순으로 섞인 것 |
| "영수증 페이로드가 남은 지연" | 절반으로 줄여도 localhost에서 무변화 |
| "인덱스 수정이 지표를 안 움직였다" | dev 서버가 **`src`가 아니라 `dist`를 서빙** — 변경이 없는 번들을 측정 |

하네스 자체의 결함도 셋 있었습니다. DOM 완료 검사가 가상화 때문에 7샘플 중 4개를 잃었고, 응답 본문 검사가 페이지네이션 때문에 40개 중 24개를 잃으며 중앙값을 위로 편향시켰으며, 공유 테이블이 측정 중 35 → 358행으로 자라 베이스라인이 코드 버전이 아니라 테이블 크기를 기술했습니다.

### 다음 측정자를 위한 필수 절차

1. **서버 변경 후에는 반드시 빌드.** dev 서버(5173)는 `packages/server/dist`에서 API를 서빙합니다.
   ```
   bun run --filter @nedian0brien/synapsenote-server build
   ```
   그 다음 vite 재시작, 그리고 `dist/index.mjs`를 grep해 변경이 들어갔는지 **확인**합니다.
2. `measurementTrustworthy`와 `rowInsertTimeouts`를 숫자보다 **먼저** 봅니다.
3. `rowInsertMedianMs`는 iteration 수가 다르면 비교 불가합니다. 샘플 i는 크기 i인 테이블에의 삽입이므로, 테이블 크기를 명시한 마지막 1/4 값을 비교합니다.
4. 측정 잔해를 남기지 않습니다. 이 작업은 850개 파일(인덱스 743 → 3 레코드)을 남겼고, 그것이 베이스라인을 오염시켰습니다.

## 종료 근거

40행 구간에서 기울기가 1.5배로 보여, 선형이면 1000행에서 ~1.4초라는 추정이 있었습니다. **틀렸습니다.**

300행 실측(`d12d90ed`, 300/300 샘플, 타임아웃 0, `measurementTrustworthy: true`):

| 지표 | 첫 1/4 | 마지막 1/4 | 증가율 |
| --- | ---: | ---: | ---: |
| `mutate` | 130ms | 72ms | 0.55 |
| `describe` | 74ms | 39ms | 0.53 |
| `query` | 9ms | 43ms | 4.87 |

테이블이 커지는데 쓰기가 빨라집니다. 중간에 바뀌는 것은 하나입니다 — **300행 중 204행이 DOM에 들어가지 않았습니다.** 그리드가 가상화하므로 약 96행을 넘으면 새 행이 렌더되지 않고, 그 렌더 비용이 사라집니다.

그것이 핸들러 계측으로 설명되지 않던 ~24ms의 정체입니다. 시나리오가 요청 종료 시각을 `fetch().then()` 콜백 안에서 찍기 때문에 메인 스레드 지연이 요청 시간에 포함되며, **0–40행은 하필 모든 삽입 행이 아직 페인트되는 구간**이었습니다. 즉 클라이언트 렌더링 비용이 쓰기로 귀속되어 있었습니다.

## 배제된 가설

전부 측정으로 죽었습니다. 다시 시도할 필요가 없다는 기록으로 남깁니다.

| 가설 | 반증 |
| --- | --- |
| 저널 기록 / 오너 재직렬화 | 기울기 0 |
| shadow git 커밋 | 40회 삽입 중 0건 발생 (Y.Doc 퍼시스턴스가 굴리는 경로) |
| 응답 직렬화 + Zod | 0.1ms, 증가율 0.91 |
| `snapshot()` 해싱 | 7 µs/행 — 자릿수 불일치 |
| 백그라운드 인덱싱 경합 | 레코드 3개 볼트에서도 동일 |
| 볼트 크기 | 743 → 3 레코드로 비워도 무변화 (`query`만 10ms → 4ms) |

## 하지 않은 것

- `query`의 9ms → 43ms 기울기. 유일하게 남은 실제 기울기이나 300행 43ms는 우선순위가 아닙니다.
- 클라이언트 렌더링 비용 자체. 가상화가 96행에서 막아주므로 실사용 문제로 관측되지 않았습니다.
- 시나리오의 `.then()` 측정 방식 교정. 요청 시간과 렌더 시간이 섞이므로, 향후 클라이언트 성능을 볼 때 먼저 분리해야 합니다.
