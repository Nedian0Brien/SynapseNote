현재 코드가 데이터베이스 정의를 읽고, Markdown 레코드를 인덱싱하고, UI·에이전트 요청을 검증된 커밋으로 바꾸는 경로를 네 가지 관점으로 정리했습니다.

01 · ARCHITECTURE

정본·파생·인터페이스의 전체 구조

읽기는 Data Plane을 통과하고, 쓰기는 동일한 경계에서 Plan + Commit Engine으로 내려갑니다.

핵심 분리: 매니페스트와 Markdown은 정본이고, 레코드 인덱스는 다시 만들 수 있는 파생 상태입니다. 커밋 영속성은 Git history와 무시된 transaction journal을 함께 사용합니다.

02 · ER / DATA MODEL

정의에서 레코드·인덱스·영수증까지

Stable ID가 객체를 연결하고, View는 값을 소유하지 않으며, Index와 Receipt는 canonical state에서 파생됩니다.

`DatabaseDefinition`은 매니페스트 그래프의 aggregate root입니다. 레코드의 `values`는 property ID로 정규화되고, 사람이 보는 key·Markdown body와 함께 원본 파일에 남습니다.

03 · SEQUENCE

셀 편집에서 검증된 커밋 응답까지

UI는 file endpoint를 직접 호출하지 않고, draft → exact plan → review → commit 프로토콜만 사용합니다.

커밋 엔진은 첫 canonical write 직전에 transaction read barrier를 올리고, 파일을 reload한 뒤 index와 postcondition을 검증합니다. 실패하면 staging의 이전 바이트로 되돌리고 derived state를 다시 만듭니다.

04 · FLOWCHART

쓰기 안전장치와 중단 지점

이 흐름의 핵심은 “항상 커밋”이 아니라, 계획 시점의 상태와 커밋 직전 상태가 여전히 같은지 확인하는 것입니다.

`snapshot_changed`, `permission_changed`, `query_snapshot_changed`, `target_changed` 같은 guard가 실패하면 부분 쓰기를 허용하지 않고 중단합니다. postcondition이 실패하면 canonical 파일과 파생 인덱스를 함께 복구합니다.

정본은 파일에 남는다

매니페스트는 `.ok/databases/*.yml`, 레코드는 database identity를 가진 Markdown/MDX입니다. Index나 server memory가 유일한 source of truth가 되지 않습니다.

읽기와 쓰기의 공통 경계

  • 읽기: catalog → describe → query → pack
  • 쓰기: draft → plan → review → commit
  • 결과: verification + revision + undo

복구는 별도 상태가 아니다

Shadow Git checkpoint, ignored transaction journal, file staging, read barrier, index rebuild가 하나의 커밋 안전장치를 구성합니다.
