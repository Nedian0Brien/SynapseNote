# SynapseNote Apple 네이티브 디자인 핸드아웃

## 문서 목적

이 문서는 SynapseNote Apple 앱 디자인 작업의 목표, 현재 상태, 실패한 접근, 다음 작업 순서와 승인 기준을 정리한다. 다음 작업자는 이 문서만 읽고도 현재 코드를 그대로 이어야 하는지, 폐기해야 하는지, 어떤 결과물을 먼저 만들어야 하는지 판단할 수 있어야 한다.

## 제품 목표

SynapseNote의 iPhone·iPad 앱을 SwiftUI로 개발한다. 현재 데스크톱 편집기의 기능을 최종적으로 이전하고, 같은 기반을 향후 macOS 앱에도 사용한다.

현재 데스크톱 앱은 다음 정보를 제공한다.

- 파일·폴더·채팅을 함께 다루는 작업 구조
- 여러 문서를 여는 탭 기반 편집 흐름
- 문서 속성, 서식 도구, 통계와 동기화 상태
- Chat, Outline, Annotations, Links, Graph, Timeline 문서 패널
- 선택한 문장과 문서를 AI 대화에 첨부하는 흐름

현재 데스크톱 UI에서 기능 목록과 정보 구조를 추출한다. Apple 앱의 시각 디자인은 별도로 수립한다.

## 확정된 조건

- SwiftUI 네이티브 구현
- iOS·iPadOS 26 우선 지원
- 향후 macOS 26 지원
- iPhone·iPad 유니버설 앱 설계
- 시뮬레이터 대신 macOS 네이티브 DesignLab에서 Retina 화면 확인
- HTML·CSS 기반 디자인 표면 제외
- 이미지 생성 기반 UI 시안 제외
- Craft를 품질 기준으로 사용하되 화면 복제 제외
- Liquid Glass는 탐색·도구 계층에서 사용
- 색이 들어간 Liquid Glass 사용 제한
- 문서·목록·표 등 콘텐츠 계층의 Liquid Glass 사용 제외
- 초기 서버는 Oracle 환경의 단일 사용자·단일 작업공간
- 서버와 데이터 모델은 향후 다중 사용자 확장을 고려
- Markdown과 메타데이터의 로컬 미러링 방향 유지

첨부파일의 지연 다운로드 기준은 아직 정하지 않았다. 파일 크기, 파일 유형, 네트워크 상태와 저장 공간 정책을 함께 정해야 한다.

이 미커밋 변경도 사용자가 승인하지 않았다. 다음 작업자는 이 코드를 디자인 기준이나 재사용 가능한 컴포넌트로 취급하지 않는다. 사용자 지시 없이 커밋·푸시·병합하거나 파괴적인 Git 명령으로 제거하지 않는다.

## 제품 디자인에서 결정해야 할 것

### 기본 인상

SynapseNote는 장문 작성, 자료 검토, 문서 연결과 AI 편집을 같은 작업 안에서 제공한다. 화면은 이 기능을 한꺼번에 노출하기보다 사용자의 현재 작업에 맞춰 필요한 계층을 보여줘야 한다.

### 시선의 시작점

문서를 열었을 때 제목과 본문이 가장 높은 우선순위를 가져야 한다. 파일 탐색, 문서 패널, 서식 도구와 AI 컨텍스트는 문서 작업을 지원하는 계층으로 배치한다.

### 제품 고유성

다음 상태와 전환에서 SynapseNote의 성격을 보여준다.

- 문장 선택 상태
- 선택 구간과 관련 문서의 연결
- 출처·검증·충돌 상태
- 선택 구간의 AI 컨텍스트 첨부
- AI 수정 결과의 검토와 적용

### 네이티브 구현의 역할

SwiftUI와 시스템 컨테이너는 창 동작, 접근성, 키보드 탐색, 포커스와 플랫폼 적응을 담당한다. 비례, 여백, 활자, 색, 선택 표현, 정보 밀도와 모션은 별도의 제품 디자인 결정이 필요하다.

## 작업 순서

1. 독립된 디자인 요소 스터디 제작
2. 실제 macOS DesignLab 실행
3. 라이트·다크 모드와 표현 강도 비교
4. 사용자 시각 승인
5. 승인 요소의 토큰·컴포넌트 승격
6. 문서 편집 화면 조립
7. 파일 탐색과 AI 문서 패널 결합
8. iPhone·iPad 적응형 구조 설계

사용자의 명시적인 승인이 다음 단계의 시작 조건이다. 승인 전에는 전체 편집 화면, 제품 셸, 모바일 화면이나 최종 디자인 시스템을 조립하지 않는다.

## 승인 기준

디자인 요소는 다음 질문에 답해야 한다.

- 설명 문구 없이 상태와 역할을 구분할 수 있는가
- 기본 SwiftUI 샘플과 구분되는 조형과 리듬이 있는가
- 문서의 가독성이 시각 효과보다 높은가
- 색은 선택·연결·상태의 의미를 전달하는가
- Liquid Glass가 콘텐츠보다 먼저 보이지 않는가
- 같은 요소가 iPhone, iPad와 Mac에서 같은 의미를 유지할 수 있는가
- 라이트·다크·고대비·Reduce Motion에서 정보가 유지되는가

다음 결과는 승인 대상에서 제외한다.

- 시스템 기본 List·Form을 나열한 화면
- 작은 회색 설명 문구가 요소의 의미를 대신하는 화면
- 현재 데스크톱 스크린샷의 열과 간격을 그대로 옮긴 화면
- 전체 제품 화면을 먼저 조립한 결과
- 파란 선택 배경과 캡슐을 모든 상태에 반복 적용한 결과
- 색이 들어간 Liquid Glass를 여러 컨트롤에 적용한 결과
- 카드와 둥근 사각형만으로 계층을 구분한 결과

## 기술 적용 시점

디자인 요소가 승인된 뒤 다음 SwiftUI API를 제품 구조에 적용한다.

- `NavigationSplitView`: 파일 탐색과 문서 편집 열
- `List(selection:)`·`OutlineGroup`: 파일과 폴더 선택
- `.searchable`: 프로젝트 검색
- `.toolbar`: 창과 문서 명령
- `.inspector`: Chat, Outline, Links 등 문서 패널
- `TextEditor`의 `AttributedString` 바인딩: 서식이 있는 편집 표면
- TextKit: SwiftUI 편집기가 충족하지 못하는 블록·선택·레이아웃 기능
- `GlassEffectContainer`: 서로 관련된 무채색 문맥 컨트롤

승인된 시각 요소와 상호작용을 이 API로 구현한다.

DesignLab은 다음 조건에서 확인한다.

- macOS 네이티브 앱 직접 실행
- 실제 Retina 배율
- 전체 창과 요소 단위 캡처
- 라이트·다크 모드
- 기본·hover·선택·비활성·오류 상태
- 키보드만 사용한 이동과 실행
- Reduce Motion·Reduce Transparency·고대비 설정

시뮬레이터 캡처, 브라우저 렌더링과 HTML·CSS 미리보기는 이 단계의 승인 근거로 사용하지 않는다.
