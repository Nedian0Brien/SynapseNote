# 브라우저 로그인 — 패스키와 비밀번호

## 문제

원격 모드에서 브라우저로 워크스페이스에 들어가려면 액세스 토큰을 붙여넣어야 한다.
50자짜리 무작위 문자열이고, 기기마다 한 번씩 필요하고, 세션이 끊기면 다시 필요하다.

토큰이 로그인 수단을 겸하는 것 자체도 문제다. 같은 토큰이 MCP 클라이언트와 CLI에서도
쓰이는 자격증명이라, 브라우저에 붙여넣기 위해 비밀번호 관리자에 넣어 두면 워크스페이스
전체 권한을 가진 문자열이 한 곳 더 늘어난다. 브라우저에서 한 번 새면 MCP 접근까지 같이
샌다.

## 원하는 결과

- 맥과 아이폰에서 Touch ID·Face ID로 로그인한다. 문자열을 입력하지 않는다.
- 패스키를 쓸 수 없는 상황에서는 비밀번호로 로그인한다.
- 브라우저 어디에도 액세스 토큰을 붙여넣는 칸이 없다.
- 액세스 토큰은 MCP·CLI 전용으로 남아 계속 동작한다.
- OAuth 동의 화면의 로그인도 같은 수단을 쓴다. 지금은 토큰 칸이다.
- 비밀번호는 저속 KDF로 저장한다. 시도 횟수 제한이 있다.

## 영향 범위

- 사용자: 운영자 한 명. 맥과 아이폰, 두 기기 이상.
- 화면: 웹앱의 `SignInGate`, OAuth 동의 화면의 로그인 단계.
- 모듈: `packages/server/src/auth/`(계정·세션), `packages/server/src/oauth/http.ts`,
  `packages/app/src/components/SignInGate.tsx`, `packages/cli/src/commands/access/`.
- 데이터: `.ok/local/`에 계정 파일이 하나 는다. 액세스 토큰 저장소는 그대로 둔다.
- 결정 권한: 운영자 본인.

## 제약

- 단일 사용자 전제를 유지한다. 계정은 하나다.
- 로컬 모드 동작은 바뀌지 않는다. 로컬은 도달 가능성이 곧 인증이므로 로그인 화면 자체가
  뜨지 않는다.
- WebAuthn은 직접 구현하지 않는다. `@simplewebauthn` v14를 쓴다. 서명 검증과 CBOR
  파싱을 손으로 짜는 것은 이 규모에서 감당할 위험이 아니다.
- 패스키는 origin에 묶인다. `https://synapse.lawdigest.kr`에 등록한 패스키는 다른
  호스트명에서 쓸 수 없다.
- 세션 쿠키 체계는 이미 있다. 새로 만들지 않고 재사용한다.

## 범위 밖

- 다중 사용자, 역할, 초대.
- 이메일 기반 비밀번호 재설정. 서버에 메일 발송 경로가 없다.
- TOTP 같은 별도 2차 인증. 패스키가 그 자리를 대신한다.
- 데스크톱 앱의 인증 방식 변경. 데스크톱은 로컬 모드다.
- 액세스 토큰 저장소 구조 변경.

## 열린 질문

1. **첫 계정과 첫 패스키를 어떻게 만드는가.** 패스키 등록에는 이미 로그인된 세션이
   필요하므로 순환이 생긴다.
   **답: CLI가 계정을 만든다.** 서버에 접근할 수 있는 사람만 계정을 만들 수 있다는 뜻이고,
   기존 `access token create`와 같은 자리에 놓인다. 만든 뒤 비밀번호로 한 번 로그인하고,
   그 세션에서 패스키를 등록한다.

2. **비밀번호를 누가 입력하는가.**
   **답: 운영자가 직접.** CLI가 대화형으로 두 번 받는다. 인자로 받지 않는다 — argv는
   `ps`와 셸 히스토리에 남고, 대화나 로그에 옮겨 적을 일도 없어야 한다.

3. **첫 계정의 사용자명.** 답: `libera3920`.
