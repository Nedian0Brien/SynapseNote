# 세 작성자가 동시에 편집해도 편집이 중복·삭제되지 않는다

## 문제

네이티브 앱(`Y.Text` 직접 편집), 웹 편집기(fragment 편집), 에이전트(agent-patch)가 한 문서를 동시에 편집하면
일부 편집이 문서에 두 번 들어가고, 드물게 사라진다. main(`d58d12fc`)과 서버 동기화 수정 머지 후(`ddabafa6`)
모두 같은 규모로 재현된다.

삽입 전용 soak(스파이크 브랜치 `native/editor-spike/scripts/soak.ts`)의 결과다. 마커는 한 번씩만 쓰므로 두 번
나오면 중복이다.

| 조건 | 마커 | 중복 | 온전히 사라짐 |
|---|---|---|---|
| main, 38줄 5분, 세 작성자 | 589 | 14 | 확인 안 함 |
| 머지 후, 38줄 5분, 세 작성자 | 534 | 17 | 약 2 |
| 머지 직전 빌드, 5,000줄 10분, 세 작성자 | 993 | 30 | 확인 안 함 |
| 웹 작성자 단독, 38줄·5,000줄 | 150씩 | 0 | 0 |

중복은 한 줄씩 생기기도 하고, 여러 문단이 한 번에 복사되기도 한다. 5,000줄 실행에서는 앱이 최근 고친 문단
47개가 한 제목 아래에 한꺼번에 들어갔다. 3-way 병합의 기준본이 양쪽보다 많이 뒤처졌을 때 충돌 해결기가 다른
쪽의 바뀐 줄을 한 충돌 구간에 넣는 결과와 모양이 같다. 이것은 가설이고 확인하지 않았다.

사용자에게는 에이전트가 문서를 고치는 동안 앱이나 웹에서 같은 문서를 만지면 문단이 복제되는 결함으로 보인다.
원격 에이전트를 쓰는 제품 방향에서 흔한 상황이다.

## 원하는 결과

1. 세 작성자 삽입 전용 soak(38줄·1,000줄·5,000줄, 각 10분)에서 중복 마커 0, 온전히 사라진 마커 0.
2. 모든 클라이언트와 디스크의 해시가 수렴하고, 문서 크기가 초기 크기 + 삽입 글자 수 × 2 안이다.
3. 찾은 원인마다 결정적으로 재현하는 테스트가 있다.
4. 웹 작성자 단독 경로의 성능(5,000줄 fragment 드레인 p95 수 ms, 반영 지연 p95 수십 ms)이 유지된다.

## 영향 범위

- 서버: Observer A 전체 경로(Path B, 잔여 병합, map-driven splice), Observer B, 저장 시 fragment 재조정.
- core: `mergeThreeWay`와 충돌 해결.
- 측정 도구(스파이크 브랜치): 다른 작성자의 동시 삽입으로 쪼개진 마커와 지워진 마커를 나눠 센다.
- 결정 권한: Dennis Park.

## 제약

- `Y.Text('source')`가 원본이다.
- 원인이 스파이크 앱의 바인딩에 있으면 서버에서 보정하지 않고 기록한 뒤 네이티브 앱 작업에서 고친다.
- 재현 테스트 없이 증상만 막는 수정은 하지 않는다.

## 범위 밖

- 5,000줄 세 작성자 부하에서 서버가 뒤처지는 문제(`large-doc-concurrent-load`).
- 서버 재시작 후 이전 문서 상태를 들고 재접속한 앱이 내용을 되살리는 문제. 스파이크 앱에 lineage 검사가 없어서
  생기며, 네이티브 앱 작업에서 다룬다.

## 열린 질문

1. **쪼개진 마커.** 다른 작성자가 방금 넣은 글자 사이에 입력이 들어가 마커가 쪼개지는 것은 CRDT 동시 편집의
   정상 결과로 보고 유실로 세지 않는다. 이 기준에 동의하는가.
2. **순서.** 부하 intent(`large-doc-concurrent-load`)와 둘 중 무엇을 먼저 할 것인가. 중복의 원인이 병합 경로라면
   부하 작업이 그 경로를 바꾸므로 이 intent를 먼저 하기를 권한다.
