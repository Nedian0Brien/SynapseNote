# 서버 문서 동기화 결함 수정

## 문제

네이티브 편집기 스파이크(`codex/native-editor-spike`, `native/editor-spike/REPORT.md`)의
동시 편집 측정에서 서버 결함 네 가지가 드러났다. 네이티브 앱은 모든 입력을 서버로
보내고 에이전트도 서버에서 문서를 고치므로, 이 결함이 남아 있으면 앱을 만들어도 긴
문서를 쓸 수 없고 입력이 사라진다.

1. **큰 문서에서 서버가 멈춘다.** 5,000줄(237k 글자) 문서에 초당 10회 편집을 넣으면
   서버는 초당 약 1.5회(`Y.Text` 편집), 0.7회(`Y.XmlFragment` 편집)만 반영한다.
   그동안 `GET /api/config`가 30초간 응답하지 않고 다른 문서도 열리지 않는다.
   38줄 문서에서는 모든 편집이 1ms 안에 반영된다.
2. **(철회, 2026-09-28) fragment 편집이 이미 반영된 입력을 지운다.** 측정 도구의 결함이었다.
   합성 fragment 작성자가 `Y.XmlText.toString()`(서식 태그 포함)으로 위치를 계산해 마커 한가운데에
   글자를 넣었고, 쪼개진 마커가 유실로 집계됐다. 고친 작성자와 웹 편집기와 같은 ProseMirror 경로
   작성자 모두 유실 0이었다(P0·P2 측정). 원하는 결과 2는 회귀를 막는 검증 기준으로 남긴다.
3. **fragment 경로에서 이스케이프가 쌓여 문서가 불어난다.** 세 클라이언트 10분
   시험에서 문서가 8.4MB가 됐고, 내용은 백슬래시가 겹겹이 쌓인 형태였다.
4. **서로게이트 쌍을 쪼개는 편집이 JS와 Rust 클라이언트를 갈라놓는다.** Yjs에서
   `a😀b`의 앞쪽 절반만 지우면 Yjs는 `a\uDE00b`(3단위), yrs는 `ab`(2단위)가 된다.
   서버는 이런 편집을 막지 않는다.

3은 웹 편집기 경로다. 웹은 후순위지만 에이전트와 웹이 같은 문서를 쓰는 동안은
데이터를 망가뜨리므로 함께 고친다.

## 원하는 결과

측정은 스파이크의 `scripts/server-load.ts`, `scripts/soak.ts`와 같은 조건(로컬 dev
서버, 5,000줄 문서는 `gen-fixture.ts` 생성본)으로 한다.

1. **큰 문서 처리량.** 5,000줄 문서에 초당 10회 편집을 30초 넣을 때, `Y.Text` 편집과
   fragment 편집 모두 모든 편집이 다른 클라이언트에 반영되고 반영 지연 p95가
   100ms 이하다. 같은 동안 `GET /api/config` p95가 100ms 이하다. 두 값은 로컬에서
   잰 서버 처리 시간 기준이다. 원격 서버에서 체감되는 값은 여기에 네트워크 왕복
   (2026-09-28 `synapse.lawdigest.kr`까지 TCP 연결 11~28ms)이 더해진다.
2. **입력 유실 없음.** 삽입 전용 soak(fragment 작성자 단독, 세 작성자 전체)에서 사라진
   마커가 0이다. 실제 y-prosemirror 클라이언트로도 같은 시험을 해서 유실이 0이다.
3. **문서 크기 안정.** 세 작성자 10분 soak(삭제 포함)이 끝났을 때 디스크·서버·앱
   해시가 30초 안에 일치하고, 문서 크기가 편집으로 넣은 양을 넘지 않는다.
   같은 Markdown을 파싱 → 직렬화 → 파싱 → 직렬화했을 때 두 직렬화 결과가 같다.
4. **서로게이트 안전.** 서로게이트 쌍을 쪼개는 편집이 어떤 경로(Yjs update,
   `agent-patch`의 `offset`, `Y.Text` 직접 편집)로 들어와도 모든 클라이언트의
   텍스트가 같게 끝난다.
5. 각 결함에 재현 테스트가 서버 테스트 체계(`server-test-manifest.ts`)에 들어간다.

## 영향 범위

- 네이티브 클라이언트: yrs 분할 규칙 패치(결함 4). 스파이크의 `yrs-ffi`에 적용하고,
  이후 네이티브 앱이 같은 패치를 쓴다.
- 서버: bridge 관찰자(`server-observers.ts`, `map-driven-splice.ts`,
  `bridge-intake.ts`), 저장(`persistence.ts`), 외부 변경 반영, agent 쓰기 경로.
- core: Markdown 파싱·직렬화(`core/src/markdown`)가 이스케이프 원인이면 함께 고친다.
- 웹 앱: 동작 변화 없음이 목표. 결함 2가 클라이언트 쪽 원인이면 범위를 다시 정한다.
- 결정 권한: Dennis Park.

## 제약

- 원본은 계속 `Y.Text('source')`(파일 전체 바이트)다. 원문 바이트 보존 규칙을 깨지 않는다.
- 로컬 데스크톱 앱과 웹 편집기의 현재 동작을 깨지 않는다. 기존 서버 테스트가 통과한다.
- 검증은 바뀐 영역의 테스트만 돌린다(AGENTS.md). 저장소 전체 검사는 하지 않는다.
- `codex/server-remote-access`와 겹치는 파일이 생기면 병합 순서를 먼저 말한다.

## 범위 밖

- 네이티브 앱 자체, Swift 파서, 데이터베이스 네이티브화.
- 여러 서버 프로세스로 부하를 나누는 구조. 한 프로세스에서 처리량을 맞춘다.
- 서버측 에이전트(마일스톤 3).

## 답이 나온 질문

사용자가 아래 권고안이 적힌 상태로 intent를 수락했다(2026-09-28).

1. **목표 수치.** → **반영 지연 p95 100ms, API p95 100ms.** 38줄 문서에서 1ms였으므로
   바뀐 블록만 처리하면 도달할 수 있는 값이다.
2. **서로게이트를 쪼개는 편집의 처리.** → **(2026-09-28 수정, 재수락됨)** 처음 채택한
   "서버가 짝 잃은 반쪽을 지운다"는 성립하지 않는다. 실험 결과:
   - Yjs는 문자열 항목을 쌍 중간에서 나눌 때 두 반쪽을 U+FFFD로 바꾼다(길이 유지). 지울
     반쪽이 거의 남지 않는다.
   - yrs 0.28은 같은 편집을 다르게 적용한다. 뒤쪽 절반 삭제는 옆 글자를 지우고, 사이 삽입은
     위치가 밀린다. 구간을 다시 써도 네 경우 중 한 경우만 수렴했다.
   - yrs의 해당 코드(`block.rs` `ItemContent::splice`)에는 Yjs 규칙이 주석으로만 남아 있다.
     그 규칙을 넣은 yrs로는 네 경우 모두 Yjs와 같은 텍스트가 됐다.

   그래서 해법을 바꾼다.
   - **네이티브 클라이언트의 yrs를 Yjs와 같은 규칙으로 고친다**(쌍 중간 분할 → 양쪽 U+FFFD).
     패치는 저장소의 `.patch` 파일로 두고 빌드 스크립트가 crates.io 소스에 적용한다.
     y-crdt 저장소에 PR을 올리는 것은 이번 범위 밖이며 따로 판단한다.
   - **서버는 쌍을 쪼개는 편집을 만들지 않는다**(diff 경계 정렬, agent API 입력 검사).
   - **서버 문서에 짝 없는 서로게이트가 남으면 U+FFFD로 바꾼다.** 반쪽을 삽입하는 편집은
     편집을 만든 문서에만 반쪽이 남고 다른 모든 클라이언트는 U+FFFD를 받기 때문이다.
