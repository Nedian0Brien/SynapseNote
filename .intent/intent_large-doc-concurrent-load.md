# 긴 문서를 세 작성자가 동시에 편집해도 서버가 뒤처지지 않는다

## 문제

5,000줄 문서를 네이티브 앱(초당 약 6.7회 `Y.Text` 편집), 웹 편집기(초당 2.5회 fragment 편집),
에이전트(agent-patch)가 10분 동안 동시에 편집하면, 서버가 8분 무렵부터 뒤처진다. 마지막 실행에서는 끝난 뒤
새 클라이언트가 15초 안에 동기화하지 못했다. 서버 동기화 수정(`ddabafa6`)으로 한 편집의 흔한 경로는 수 ms로
줄었지만, 드물게 타는 경로가 문서 크기에 비례해 수 초씩 걸린다.

측정으로 확인한 비용:

- **Observer A 전체 경로.** 빠른 경로 조건을 못 맞춘 웹 편집(표·컴포넌트·새 블록·재파싱 불일치, 약 1~5%)은
  문서 전체를 직렬화·파싱한다. 5,000줄에서 1초 이상. 웹 작성자 단독 5,000줄 실행의 반영 지연 p95가 1.6~2.0초인
  이유다.
- **충돌 병합.** 3-way 병합은 충돌이 있으면 문서 전체로 다시 돈다(출력 보존을 위해). node-diff3 LCS가 5,000줄
  문서에서 한 번에 5.7~13.8초.
- **MDX 폴백 문서.** `{`, `<`처럼 MDX 파싱이 실패하는 글자가 든 문서는 분할 폴백 파싱을 타서 블록 범위가 없고,
  편집마다 전체 파싱(5,000줄 1.2초 이상)을 한다.
- **저장 검사.** 로드·파일 감시·에이전트의 paired write 뒤에는 fragment가 텍스트의 파싱 결과로 표시되지 않아,
  저장마다 전체 파싱·직렬화를 한다.

마지막 실행이 뒤처진 직접 원인은 프로필을 뜨지 않아 확인하지 못했다.

## 원하는 결과

1. 5,000줄 세 작성자 10분 soak에서 반영 지연 p95 ≤ 300ms, 최대 ≤ 2초, `GET /api/config` p95 ≤ 100ms.
   끝난 뒤 새 클라이언트가 5초 안에 동기화한다.
2. 웹 작성자 단독 5,000줄 실행의 반영 지연 p95 ≤ 300ms(현재 1.6~2.0초).
3. MDX 폴백 문서에서도 편집이 닿지 않은 블록은 다시 파싱하지 않는다.
4. 각 경로의 비용을 `/api/metrics/reconciliation`에서 경로별로 볼 수 있다(현재 경로 횟수만 있음).

## 영향 범위

- 서버: Observer A 전체 경로, 병합 호출, 저장 경로.
- core: 분할 폴백 파서(`parse-with-fallback.ts`), `mergeThreeWay`.
- 측정: `bench-bridge-drain.ts`, 스파이크 브랜치의 soak·부하 스크립트.
- 결정 권한: Dennis Park.

## 제약

- 출력 바이트는 지금과 같아야 한다. 빠른 경로는 전체 경로와 같은 결과를 증명할 수 있을 때만 쓴다(증분 파서·
  병합 퍼징과 같은 차등 테스트).
- 관찰자 작업을 워커 스레드로 옮기지 않는다(Y.Doc 공유 불가, 이전 spec에서 버린 대안).

## 범위 밖

- 동시 편집의 중복·삭제(`concurrent-edit-duplication`).
- 네이티브 앱 쪽 성능.

## 열린 질문

1. **목표 수치.** 위 수치(p95 300ms, 최대 2초)는 원격 서버의 네트워크 지연을 빼고 잡은 제안값이다. 이 기준으로
   할 것인가.
2. **폴백 노드의 위치 속성.** `rawMdxFallback`의 `originalSpan`은 분할 구간 기준 오프셋이라, 증분 결과를 전체
   파싱과 같게 맞추려면 이 값을 문서 기준으로 바꿔야 할 수 있다. 이 값을 읽는 곳을 확인한 뒤 정한다.
